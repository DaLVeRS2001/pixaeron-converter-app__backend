6. Move Auth off the Lightsail master user onto a dedicated least-privilege role.
   Confirmed not started: no `pixaeron_auth` role exists anywhere in the
   repository, and `dbauth` is still owned by `dbmasteruser`.
   - The master user can read and drop every database on the instance, including
     the Notifications database, and can create or drop roles. A compromise of
     Auth therefore compromises the whole instance.
   - Target: a `pixaeron_auth` login role owning only `dbauth`, mirroring what
     Notifications does from the start. Keep the master password for operator
     administration only.
   - Not zero-downtime-free: create the role, transfer ownership of the schema
     and every object in `dbauth`, update `DATABASE_URL` in Parameter Store,
     redeploy Auth. Snapshot first and rehearse on a restored copy.
   - Generate the password from letters and digits only so it needs no
     percent-encoding inside `DATABASE_URL`; if it does contain other
     characters, encode with `[uri]::EscapeDataString('<password>')` exactly
     once — double-encoding turns `%7B` into `%257B` and breaks authentication.
   - While in there: `REVOKE CONNECT ON DATABASE dbauth FROM PUBLIC`. Today any
     role on the instance can connect to `dbauth`; table privileges still block
     reads, so only catalogue metadata is exposed, but the grant is pointless.

7. Registration leaks account existence — DECIDED 2026-08-12: keep (Option A).
   `registration.service.ts:63-68` (and the P2002 race branch) throw
   `EMAIL_ALREADY_REGISTERED`, and the code is public in
   `graphql-error-contract.ts:9`, so registration answers truthfully whether an
   address has an account. Owner accepts the trade-off for the clearer UX.
   Verified mitigations that make bulk enumeration expensive: registration
   requires a solved Turnstile captcha on every attempt
   (`registration.service.ts:52` calls `requireCaptcha` unconditionally when
   captcha is enabled — not "if needed"), and the shared HTTP rate limit fronts
   the endpoint. Note the escalating limits (cooldown, attempt counter, block)
   protect login and the email actions, not registration itself; registration's
   brake is the captcha-per-attempt cost.
   If this is ever revisited, Option B is recorded in git history of this file:
   always answer "check your email", mail "someone tried to register" to
   existing addresses (a third purpose in the gRPC contract), remove the code
   from `publicErrorCodes`, echo the normalized input address from the resolver,
   and delete five frontend references.

8. ACCEPTED BEHAVIOUR, not tasks. Recorded so nobody "fixes" them later.

   (a) Password recovery sends nothing for a Google-only account.
   `password-recovery.service.ts:56` mails the reset link only
   `if (user?.password)`; an account created through Google Sign-In has no
   password, so an audit event is recorded and no mail is sent, while the form
   still answers "if the account exists, the message is on its way". Confirmed
   in production on 2026-08-11 — no `email_deliveries` row is created at all.
   The generic answer is deliberate: a different response would reveal how the
   account was registered. Owner decision (2026-08-11): keep the backend as is —
   sending a "you signed up with Google" mail would mean a third purpose in the
   gRPC contract for little gain.
   Closed on the frontend instead: the recovery form carries a permanent hint
   ("Signed up with Google? A reset link will not arrive — use Continue with
   Google"), rendered unconditionally so it cannot react to the entered address
   and therefore leaks nothing. Do not make that hint conditional.

   (b) A used reset link still renders the form; the failure appears only after
   submitting ("this link has already been used"). Single use is enforced in the
   database — `password-recovery.service.ts:110` checks `consumedAt` before the
   transaction, `:148` repeats it inside, and `:173-176` consumes through a
   compare-and-swap on `consumedAt: null` and `expiresAt > now`, so two
   simultaneous clicks cannot both succeed. Validating the token on page load
   would be friendlier but would turn the page into a token-validity oracle that
   answers without hitting the submit rate limit. Owner decision (2026-08-11):
   keep as is.

10. Error messages now follow a language switch — DONE (2026-08-11).
   The five auth models store `{ code, action, retryAfter }` and translate on
   render, so switching language re-renders the visible error.
   `translateAuthError` split into `resolveAuthError` and `authErrorMessage`,
   which makes error state assertable without i18n.
   Closed at the same time: `TOO_MANY_REQUESTS` and `SERVICE_UNAVAILABLE` were
   produced by `shared/api/errors.ts` but had no message, so a Redis outage
   rendered "Something went wrong"; `CAPTCHA_INVALID` was aliased to
   "Complete the CAPTCHA verification", which was misleading; the three
   attempt-limit codes reached the generic fallback whenever `retryAfter` was
   absent; and `errors.googleUnavailable` was set as a bare literal with no code.
   Still open, same root cause, different place: every zod schema in
   `features/auth/model/schemas.ts` bakes translated strings into resolver
   output, and `useSignUpModel` writes `t('validation.terms')` into react-hook-
   form state. Field-level validation errors therefore still do not follow a
   language switch.

11. Deferred code work.
   - HMAC-alias convergence — DONE (2026-08-11). The nonterminal path in
     `ses-feedback-transitions.ts` now converges every non-blocked alias onto
     the authoritative watermark, as the terminal path already did. Without it,
     a two-version keyring could leave one alias `TEMPORARY_FAILURE@T10` and
     another `ACTIVE@T5`; the retention cron then deletes the retired-key row
     holding the correct watermark and the regression becomes permanent. The
     convergence is skipped when the keyring has a single version, so the hot
     path is unchanged today.
   - gRPC command-channel authentication — CODE DONE (2026-08-12), enforcement
     off until the operator enables it. Both sides read the optional
     `NOTIFICATIONS_COMMAND_SECRET`: the Auth client sends it in the
     `x-pixaeron-command-secret` metadata key when set, and a `CanActivate`
     guard on the Notifications controller compares SHA-256 digests with
     `timingSafeEqual` and rejects with `UNAUTHENTICATED` when set. Unset on
     either side keeps today's behaviour, so the code deploys with zero risk.
     To enable: create the same >=32-char secret at
     `/pixaeron/production/notifications/NOTIFICATIONS_COMMAND_SECRET` and
     `/pixaeron/production/auth/NOTIFICATIONS_COMMAND_SECRET`, add
     `NOTIFICATIONS_COMMAND_SECRET` to both services' `secureParameters` in
     `.github/deploy-services.json`, and release. The ordered release restarts
     Notifications (enforcing) before Auth (sending), so security emails can
     fail with UNAUTHENTICATED for the one-to-two-minute window between the two
     restarts — enable during a quiet hour. TLS/mTLS remains unnecessary while
     the channel stays inside one Docker host (`notifications_command` is
     `internal: true`, port 50052 unpublished).
   - Central CI compose rollback baseline — DONE (2026-08-12). The compose file
     is a whole-stack artifact, so `pixaeron.yml` now installs it once per
     release before the service loop, keeps one `release-rollback` backup,
     restores it in a `failure()` step, discards it on success, and cleans the
     staged copy in the `always()` step. `deploy-service.sh` no longer touches
     the compose file at all; its rollback restarts the service with `--no-deps`
     so a rollback cannot re-resolve dependencies against a mid-release stack.
     A failed release now leaves the pre-release compose on disk, and rerunning
     the same commit behaves like a first run.
   - `workflow_dispatch` naming a single service — DONE in the central CI
     (2026-08-11), pending a new pin. The earlier diagnosis — "an empty deploy
     matrix" — was WRONG. `service=notifications` selects one row: notifications
     is in `.github/deploy-services.json`, it has no `schema-check` target so the
     subgraph guard does not fire, and an unknown name hard-fails an earlier
     step. The two real paths to a green run that deployed nothing were the
     unannounced `github.ref == 'refs/heads/main'` job gate and `release_guard`
     setting `deploy=false` when `git ls-remote` shows main has moved, after
     which every later step is skipped and the job still reports success.
     `pixaeron.yml` now writes the selection to the step summary, exposes
     `released` from `deploy-release`, and ends in a `release-outcome` job that
     turns a manual release on main which deployed nothing into a red run and
     explains a verification-only dispatch on any other ref. It is scoped to
     `workflow_dispatch`, so `pull_request` and push-to-main are untouched.

     That guard immediately caught the real defect, which neither earlier
     diagnosis had found. A dispatch with `service=notifications` on main showed
     `has_deployments=true` and a selection of `["notifications"]`, yet
     `build-images` and `deploy-release` were skipped. Cause: `notifications` is
     not a GraphOS subgraph, so `selected_subgraphs` is empty,
     `graphos_check_required` is false and `graphos-check` is skipped — and
     because neither `build-images` nor `deploy-release` carried a status-check
     function in its `if`, GitHub's implicitly inserted `success()` propagated
     that skip transitively down the chain. `verification-gate` did not stop it:
     its own `always()` rescues only itself, not what depends on it. This is
     actions/runner#2205, open since 2022.
     Fixed by prefixing both jobs' conditions with `!cancelled() &&`. Nothing
     else changes — both jobs already require `verify` and `verification-gate` to
     be `success` explicitly, so the implicit gate was contributing only the bug.
     Note the defect was never dispatch-specific: a push to main touching only
     non-subgraph services (that is, notifications alone) skipped its release the
     same way and stayed green. Check whether any notifications-only change on
     main was never actually deployed.
   - Cross-service duplication — DONE (2026-08-12). `libs/config`
     (`@pixaeron/config`) now owns the shared Joi primitives (`booleanValue`,
     `nodeEnvironment`, `port`, `postgresUrl`) and `normalizeEmail`, which both
     services import; the notifications-side `normalizeRecipient` copy is gone.
     That function is a cross-service contract: auth normalizes before the wire,
     notifications before HMAC-ing, and drift would silently break suppression.
     Deliberately NOT deduplicated: `prisma.service.ts` is byte-identical across
     both apps but each extends its own generated client, so a generic factory
     is not worth it for two services.
   - Auth `User` table rename — DONE (2026-08-12), rode the least-privilege
     release: migration `20260812000000_rename_user_table` renames the table to
     `users` with its named constraints, unique indexes and sequence,
     `@@map("users")` in the schema, and the one raw-SQL site in
     `session.service.ts`. Proven by applying the full 11-migration chain on a
     throwaway Postgres. Remember it is not backward-compatible: rolling Auth
     back past this release needs the inverse DDL, not just an image revert —
     the pre-release snapshot from the role migration covers that.
   - `.gitattributes` — DONE (2026-08-11) in all three repositories, together
     with re-encoding `README.md` from UTF-16LE to UTF-8 and a renormalize pass
     in its own commit. Add that commit to `.git-blame-ignore-revs` if blame
     noise ever matters.
