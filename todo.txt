6. Move Auth off the Lightsail master user onto a dedicated least-privilege role.
   Confirmed not started: no `pixaeron_auth` role exists anywhere in the
   repository, and `dbauth` is still owned by `dbmasteruser`.
   - The master user can read and drop every database on the instance, including
     the Notifications database, and can create or drop roles. A compromise of
     Auth therefore compromises the whole instance.
   - Target: a `pixaeron_auth` login role owning only `dbauth`, mirroring what
     Notifications does from the start. Keep the master password for operator
     administration only.
   - Not zero-downtime-free: create the role, transfer ownership of the schema
     and every object in `dbauth`, update `DATABASE_URL` in Parameter Store,
     redeploy Auth. Snapshot first and rehearse on a restored copy.
   - Generate the password from letters and digits only so it needs no
     percent-encoding inside `DATABASE_URL`; if it does contain other
     characters, encode with `[uri]::EscapeDataString('<password>')` exactly
     once — double-encoding turns `%7B` into `%257B` and breaks authentication.
   - While in there: `REVOKE CONNECT ON DATABASE dbauth FROM PUBLIC`. Today any
     role on the instance can connect to `dbauth`; table privileges still block
     reads, so only catalogue metadata is exposed, but the grant is pointless.

7. Registration leaks account existence — decision still open.
   `registration.service.ts:63-68` (and the P2002 race branch at `:112-115`)
   throw `EMAIL_ALREADY_REGISTERED`, and that code is in the public allowlist in
   `graphql-error-contract.ts:9`, so both the code and the message go to the
   client. Every other email flow is privacy-preserving: password reset and
   resend always return `{ accepted: true }`.
   Important: **the code itself is the oracle**, so rewriting only the message
   changes nothing — Option B must also remove the code from `publicErrorCodes`.
   - Option A (keep): accept the trade-off for the clearer UX and record it as a
     deliberate decision.
   - Option B (close): always answer "check your email"; send verification to a
     new address and "someone tried to register with your address" to an
     existing one. Cheaper than it looks: only the P2002 branch is spec-covered
     (`registration.service.spec.ts:152`), the frontend cost is deleting five
     references to `emailAlreadyRegistered`, and the success path already does
     the right thing — `useSignUpModel.ts` navigates to `/verify-email` on
     `accepted`. One backend detail: the existing-account branch creates no row,
     so the resolver must echo the normalized input address rather than
     `registration.user.email`.
   Decide before public launch rather than by default.

8. ACCEPTED BEHAVIOUR, not tasks. Recorded so nobody "fixes" them later.

   (a) Password recovery sends nothing for a Google-only account.
   `password-recovery.service.ts:56` mails the reset link only
   `if (user?.password)`; an account created through Google Sign-In has no
   password, so an audit event is recorded and no mail is sent, while the form
   still answers "if the account exists, the message is on its way". Confirmed
   in production on 2026-08-11 — no `email_deliveries` row is created at all.
   The generic answer is deliberate: a different response would reveal how the
   account was registered. Owner decision (2026-08-11): keep the backend as is —
   sending a "you signed up with Google" mail would mean a third purpose in the
   gRPC contract for little gain.
   Closed on the frontend instead: the recovery form carries a permanent hint
   ("Signed up with Google? A reset link will not arrive — use Continue with
   Google"), rendered unconditionally so it cannot react to the entered address
   and therefore leaks nothing. Do not make that hint conditional.

   (b) A used reset link still renders the form; the failure appears only after
   submitting ("this link has already been used"). Single use is enforced in the
   database — `password-recovery.service.ts:110` checks `consumedAt` before the
   transaction, `:148` repeats it inside, and `:173-176` consumes through a
   compare-and-swap on `consumedAt: null` and `expiresAt > now`, so two
   simultaneous clicks cannot both succeed. Validating the token on page load
   would be friendlier but would turn the page into a token-validity oracle that
   answers without hitting the submit rate limit. Owner decision (2026-08-11):
   keep as is.

9. Verify-email page — DONE (2026-08-11).
   The header no longer renders pending instructions once the address is
   confirmed, and an authenticated user whose address is already verified now
   sees the confirmed state instead of a resend form that silently sends
   nothing. The state comes from `emailVerified` on the `me` query, which the
   frontend already selected, so no schema change was needed. The override is
   gated on the page's own status still being `CHECK_EMAIL`, so a real token
   outcome always wins, and anonymous visitors are untouched — anything else
   there would be an enumeration oracle.

10. Error messages now follow a language switch — DONE (2026-08-11).
   The five auth models store `{ code, action, retryAfter }` and translate on
   render, so switching language re-renders the visible error.
   `translateAuthError` split into `resolveAuthError` and `authErrorMessage`,
   which makes error state assertable without i18n.
   Closed at the same time: `TOO_MANY_REQUESTS` and `SERVICE_UNAVAILABLE` were
   produced by `shared/api/errors.ts` but had no message, so a Redis outage
   rendered "Something went wrong"; `CAPTCHA_INVALID` was aliased to
   "Complete the CAPTCHA verification", which was misleading; the three
   attempt-limit codes reached the generic fallback whenever `retryAfter` was
   absent; and `errors.googleUnavailable` was set as a bare literal with no code.
   Still open, same root cause, different place: every zod schema in
   `features/auth/model/schemas.ts` bakes translated strings into resolver
   output, and `useSignUpModel` writes `t('validation.terms')` into react-hook-
   form state. Field-level validation errors therefore still do not follow a
   language switch.

11. Deferred code work.
   - HMAC-alias convergence — DONE (2026-08-11). The nonterminal path in
     `ses-feedback-transitions.ts` now converges every non-blocked alias onto
     the authoritative watermark, as the terminal path already did. Without it,
     a two-version keyring could leave one alias `TEMPORARY_FAILURE@T10` and
     another `ACTIVE@T5`; the retention cron then deletes the retired-key row
     holding the correct watermark and the regression becomes permanent. The
     convergence is skipped when the keyring has a single version, so the hot
     path is unchanged today.
   - The private Auth -> Notifications gRPC channel has no TLS and no
     authentication, and raw one-time tokens travel over it together with the
     plaintext recipient address. Note `createInsecure()` appears nowhere in
     application code — the channel is insecure by omission: neither
     `main.ts:27-34` nor `auth.module.ts:42-52` passes `credentials`, and Nest
     falls back to insecure. The controller takes `_metadata` and never reads
     it. Exposure is contained: `notifications_command` is `internal: true`,
     port 50052 is unpublished, and the server binds only the network alias.
     Minimal fix before a second consumer joins: a shared secret in metadata
     compared with `timingSafeEqual` in a guard — not mTLS, which buys nothing
     against an attacker who already has container access.
   - Central CI rollback restores the compose file from the wrong baseline for
     the second and later services of an ordered release. Confirmed by reading
     `deploy-service.sh:23,37-40,106,154` against the per-service `scp` inside
     the deploy loop — no staging VPS is needed to see it. Service #2 backs up
     service #1's already-installed new compose, and service #1's success path
     has already deleted the true baseline. Fix by removing the bug class: the
     compose file is a whole-stack artifact, so install it once per release,
     back it up once, restore it on failure, and take it out of per-service
     rollback entirely.
   - `workflow_dispatch` naming a single service. The earlier diagnosis — "an
     empty deploy matrix" — is WRONG. On the pinned revision `service=notifications`
     selects one row: notifications is in `.github/deploy-services.json`, it has
     no `schema-check` target so the subgraph guard does not fire, and an
     unknown name hard-fails an earlier step. Two real paths remain to a green
     run that deployed nothing, and neither is announced: the release jobs are
     gated on `github.ref == 'refs/heads/main'`, and `release_guard` sets
     `deploy=false` when `git ls-remote` shows main has moved, after which every
     later step is skipped and the job still reports success.
     Fix regardless of which one it was: log the selection in the matrix step,
     expose from `deploy-release` whether a release actually executed, and fail
     an explicit dispatch that verified successfully on `main` and released
     nothing. Do not weaken the `has_deployments` job gate — `pull_request` runs
     are intentionally empty and depend on it.
   - Remaining duplication. Already extracted: `Transaction`,
     `isUniqueConstraintError` (both services now), `recipientHashFilter`,
     `matchesRecipientHash`, the SES sender parser and the lease-expiry payload.
     Left: the cross-service Joi primitives (`booleanValue`, `NODE_ENV`, `PORT`,
     `DATABASE_URL`), which need a new `libs/config` — not `libs/nestjs`, whose
     barrel pulls in express and would give a gRPC-only service an HTTP-server
     dependency. Bundle that move with `normalizeEmail` / `normalizeRecipient`,
     which are the same function in both services and are a cross-service
     contract rather than a three-line helper: if they drift, the recipient hash
     stops matching and suppression silently stops applying. `prisma.service.ts`
     is byte-identical across both apps but each extends its own generated
     client, so deduplicating it needs a generic factory — not worth it for two
     services.
   - Auth `User` has no `@@map`, so its table is `"User"` while every other
     model maps to snake_case plural. The rename is metadata-only DDL — table,
     `User_pkey`, `User_id_seq`, two unique indexes and one check constraint;
     the four child foreign keys are already snake_case and follow the table by
     OID. But it is not backward-compatible: the previous image's
     `session.service.ts:78` runs `SELECT "password" FROM "User"` in raw SQL and
     would 500 after the rename, so rollback needs the inverse DDL rather than
     an image revert. Schedule it alone, with a snapshot.
   - `.gitattributes` — DONE (2026-08-11) in all three repositories, together
     with re-encoding `README.md` from UTF-16LE to UTF-8 and a renormalize pass
     in its own commit. Add that commit to `.git-blame-ignore-revs` if blame
     noise ever matters.
